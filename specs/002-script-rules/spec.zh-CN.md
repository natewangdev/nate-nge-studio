## 用户场景与测试 *(必填)*

### 用户故事 1 - 可复用的 Studio 脚本 Rule 循环（优先级：P1）

脚本作者使用 Studio 提供的、借鉴旧 Bot 的 Rule 辅助库编写协作式 `run(engine, ctx)`：具名规则含优先级与冷却、可选共享状态、每 tick 可选只执行一条。启动、暂停、结束与运行时长超时仍由现有 UI 与 `RunContext` 拥有。

**优先级理由**：没有共享辅助库，每脚本会自造决策环并偏离既有 Rule 理念。

**独立测试**：用假引擎与假 `RunContext` 单测辅助库：注册两条不同优先级规则；断言 `one_action_per_tick` 时仅高优先级行动规则触发；断言暂停期间不评估；断言结束后循环迅速退出。

**验收场景**：

1. **给定**脚本注册了多条带优先级的规则，**当**同一 tick 内多于一条将返回 `True`，**则**在启用每 tick 单动作时仅最高优先级且就绪的规则行动。
2. **给定**某规则有冷却且刚返回 `True`，**当**冷却未结束时进入后续 tick，**则**跳过该规则直至再次就绪。
3. **给定** Studio 处于暂停，**当**规则循环将开始新 tick，**则**通过 `wait_if_paused` / `checkpoint` 等待，在恢复或请求结束前**不**评估任何规则。
4. **给定** Studio 结束或运行时长超时在 `RunContext` 上置停止，**当**循环观察到 `should_stop`，**则**退出，且脚本无需自建会话总时长定时器。
5. **给定**作者从 Studio 导入辅助库，**当**其编写新目录脚本，**则**可注册规则并运行循环，而无需从旧引擎复制 Bot 代码。

---

### 用户故事 2 - Smoke 用 Rule 示范真实 NGE2 I/O（优先级：P1）

已打包的 `demo/smoke` 的 `run` 改为使用 Rule 辅助库。至少一条规则调用真实 NGE2 感知和/或控制 API（不仅打日志）。生命周期（启动/暂停/结束/时长）完全由 Studio 驱动。

**优先级理由**：Smoke 是主要示教样例，须展示 Rule 与 Studio 所有权切分，并真实使用引擎。

**独立测试**：在 Studio（或等价环境）用真实或可记录调用的 NGE2 运行 smoke；启动 → 观察规则驱动的引擎使用；暂停 → 无后续规则动作；恢复 → 继续；结束或超时 → 空闲且由 Studio 关闭引擎。

**验收场景**：

1. **给定**选中 smoke 并以合法参数启动，**当**运行处于活动状态，**则**至少一条已注册规则调用 NGE2 感知和/或控制方法（如构造引擎上可用的 find/capture/move/click 族）。
2. **给定** smoke 正在运行，**当**操作者按下暂停，**则**规则评估停止，直至恢复（暂停时启动/F9）。
3. **给定** smoke 正在运行，**当**操作者按下结束或 Studio 时长到期，**则**脚本协作式返回且 Studio 关闭引擎；smoke **不**自行实现会话总时长或框架级 pause。
4. **给定** CI/假引擎环境，**当**测试行使 smoke 或辅助库，**则**真实 I/O 规则仍针对引擎 API 表面表达（spy/假实现可打桩），样例在无 HID 硬件时仍有效。

### 用户故事 3 - 文档化 Rule 所有权边界（优先级：P2）

作者可读本功能的契约/quickstart，理解 Rule 与 Studio 各自拥有什么，以及相对旧 Bot 明确不做的能力（`session_max_seconds`、tick 抖动、`break_every`）。

**优先级理由**：防止把宿主职责重新塞进脚本 Rule。

**独立测试**：文档检查清单 — 写明 Studio 拥有启停/暂停/时长/引擎关闭；辅助库仅提供精简 Rule 循环；smoke 指向该辅助库。

**验收场景**：

1. **给定**功能文档，**当**作者查找辅助库上的会话时长或 pause API，**则**找不到；文档导向 Studio UI / `RunContext`。
2. **给定**功能文档，**当**作者与旧 Bot 对比，**则**可见有意省略的能力（jitter、break_every、session_max）。

---

### 边界情况

- 规则抛错：辅助库**必须**隔离失败（按文档策略记录日志并继续或结束本 tick），避免坏规则妨碍 Studio 结束处理；倾向本 tick 记录并跳过后续评估，除非已请求停止。
- 冷却为 `0`：规则在返回 `True` 后下一 tick 仍可再触发。
- 规则列表为空：循环仍遵守暂停/结束，空转不行动。
- 假引擎缺少感知/控制：smoke 的真实 I/O 规则**必须**以清晰日志降级并返回 `False`（或等价），而非打崩工作线程，以便 Studio 仍可干净结束。
- 规则内长时间阻塞超过 Studio 挂起宽限：不要求强制杀死；作者**应当**保持规则体简短，并依赖 tick 边界的暂停/结束检查。

## 需求 *(必填)*

### 功能需求

- **FR-001**：系统**必须**在 Studio 包内提供可复用的 Rule 循环辅助库（非内嵌旧版 `nge.bot`），供目录脚本 `run(engine, ctx)` 使用。
- **FR-002**：Rule **必须**至少包含：名称、优先级、冷却秒数，以及可调用 `fn(rule_ctx) -> bool`（`True` 表示本 tick 已行动）。
- **FR-003**：辅助库每 tick **必须**按优先级评估就绪规则；在配置为每 tick 单动作（默认开启）时，首个返回 `True` 后**必须**停止继续评估。
- **FR-004**：仅当规则返回 `True` 时，辅助库**必须**刷新该规则冷却。
- **FR-005**：每个 tick **必须**以协作式 Studio 暂停/结束处理开始（`wait_if_paused` / `checkpoint` / 等价）。暂停期间辅助库**不得**评估任何 Rule。
- **FR-006**：辅助库**不得**实现 Studio 运行时长、启动、暂停或结束；这些仍归 Studio UI + `RunContext` + 现有 runner 超时。
- **FR-007**：辅助库**不得**提供旧 Bot 的 `session_max_seconds`、tick 抖动或 `break_every` / `break_duration` 拟人休息调度。
- **FR-008**：辅助库**必须**暴露规则间共享可变状态（旧 `ctx.state` 类比），且与 Studio `RunContext` 区分。
- **FR-009**：`demo/smoke` **必须**改写为使用该辅助库，且**必须**注册至少一条对所提供 `engine` 调用真实 NGE2 感知和/或控制 API 的规则。
- **FR-010**：Smoke 与辅助库**必须**兼容 Studio 单实例 runner 以及 `finally` 中的引擎 `close()`。
- **FR-011**：自动化测试**必须**覆盖辅助库的优先级、冷却、暂停门控与结束退出，且不要求 HID 硬件。

### 关键实体

- **Rule**：具名决策单元（优先级、冷却、`fn`）；返回是否已行动。
- **RuleContext**：传给规则的每 tick（或每 run）上下文：可访问 `engine`、共享 `state`，以及辅助库文档化的薄适配（不得取代 Studio `RunContext`）。
- **RuleLoop / ScriptBot**（名称可定）：托管规则列表与绑定 Studio `RunContext` 的 tick 循环。
- **Shared State**：作者拥有的 dict/对象，供跨规则阶段机使用。

## 成功标准 *(必填)*

### 可衡量结果

- **SC-001**：新脚本作者仅凭本功能辅助库文档 + smoke 参考，可在 30 分钟内接好三条优先级规则并在 Studio 暂停/结束下运行。
- **SC-002**：合规 smoke 运行时，暂停信号后 2 秒内停止后续规则动作（与 Studio SC-003 精神对齐）。
- **SC-003**：辅助库单元测试在无 ESP32/HID 硬件的 CI 中通过。
- **SC-004**：Smoke 真实 I/O 规则在源码中可见（调用引擎感知/控制 API）；假引擎测试仍经桩行使该调用路径。

## 假设

- 旧 nate-gaming-engine Bot 仅为**设计参考**；不把该仓代码导入 Studio。
- NGE2 仍为唯一引擎；Rule 辅助库适配 Studio 构造的 `engine` 实例。
- 功能 `001` 的 MVP 入口 `def run(engine, ctx)` 不变；本功能在其上增加可选推荐模式。
- 「真实 NGE2 I/O」指调用公开的视觉/查找和/或 HID 控制 API；实现时可选用最轻量且可打桩的可靠调用以证明路径。
- Tick 节奏可为辅助库上的简单固定间隔（无抖动），足以示范；精确 Hz 调优不是产品硬性要求，实现方可提供基础可配置间隔。
